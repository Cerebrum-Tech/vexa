---
title: "Report after every meeting"
description: "When a call ends, an agent writes notes, decisions, and follow-ups into your workspace."
---

Once a meeting produces a transcript, an [agent](/core/agents) can read it **through your
[workspace](/concepts#workspace)** — grounding the write-up in what you already know about the people and
the deal — and commit a report. Because the transcript is trusted input, the agent both reads and writes;
git is the undo.

For a [planned meeting](/how-to/plan-a-meeting) with a bound workspace this closes the loop: the
transcript lands on the same meeting record the plan started as, and the report lands in the same
workspace the attendees already share.

## Automatic Turkish report on meeting end

The meeting worker updates `kg/entities/meeting/<native-id>.md` when it receives `session_end` and
retains the completed report at `kg/entities/meeting/<native-id>.run-<meeting-row-id>.md` for that
specific run. Recurring meetings therefore keep their earlier summaries. Configure the workspace's
visible `agents/meeting.md` frontmatter:

```yaml
enabled: false
write_meeting_doc: true
report_language: tr
model: gemma4:12b
```

`enabled: false` skips continuously refreshed model beats; it does not disable transcript notes or
the final document turn. The Turkish report contains exactly `## Özet`, `## Alınan Kararlar`, and
`## Aksiyon Maddeleri`. Decisions require an explicit commitment in the transcript. Action owners
are retained only when stated; otherwise the report says `Sorumlu belirtilmedi`.

Correction is enabled by default. The meeting owner can turn processing off during a live meeting;
that explicit preference is retained and prevents further model beats and the final report turn.
Changing the displayed transcript in a shared meeting changes only the viewer's local view.

The browser's **Özet** tab and **Bildirimler** menu recognize completion from producer-stamped run,
workspace and content revision metadata. The producer validates the report, commits its readiness metadata and per-run copy through the
governed writer, and confirms that both exact files reached workspace history. Preparation notes, a report
from another run on the same join link, and inaccessible files do not produce a ready indicator.
Notifications are observed while other pages are open; opening one returns to its canonical meeting.

The meeting owner can select **Özeti düzenle**, change the summary, and click **Kaydet**. Typing does
not save. **Vazgeç** discards the draft. Decisions and action items remain separate. Saving checks the
report revision and workspace write access, and confirms the worker's commit before showing success.
A conflicting update keeps your draft so you can review the latest report before trying again.

Named people and companies supported by the generated report become pages in the same workspace's
**Kişiler** and **Şirketler** directories. Each page includes the exact source excerpt and a link to
the meeting run. Matching titles and aliases reuse existing pages while preserving their notes;
ambiguous matches are left unchanged. Default workspaces start without demo people or companies.
When the document's entity metadata provides no usable report evidence, the worker extracts names
from the finished report through the configured completion provider and validates each quoted mention.
If that provider is unavailable, the report is retained and no unsupported entity page is created.

## Long meetings, small context windows

A meeting has no maximum length; your model's context window does. `VEXA_LLM_CONTEXT_TOKENS`
(default `8000`) is the budget every prompt the worker sends is held to — set it to your model's
real window.

When a transcript fits, it goes to the report verbatim: raw transcript is always better evidence
than a summary of it. When it does not, the worker **summarizes the meeting in chunks that fit and
writes the report from those digests** — so an hour of conversation, or a two-hour
[uploaded recording](/how-to/upload-a-recording), is represented end to end rather than truncated at
the point where the decisions usually are. The cost is one extra model call per chunk. A digest call
that fails falls back to its own chunk's transcript, so a lost call costs detail, never a stretch of
the meeting.

The report turn carries its evidence and its frontmatter in the prompt and writes the file in one
shot. It deliberately never opens the transcript file: a file read is context that cannot be
measured or capped, and that is what made a budget unenforceable before.

<Note>
`VEXA_LLM_MAX_TOKENS` caps the *reply*, not the request. Leave it unset to let the backend decide —
a truncated report is worse than a long one.
</Note>

For a one-GPU local test with Ollama, bind the server to the Docker bridge gateway instead of a LAN
interface. On a standard Linux Docker installation, first verify the gateway:

```bash
docker network inspect bridge --format '{{(index .IPAM.Config 0).Gateway}}'
# Example result: 172.17.0.1
```

Start Ollama with that exact address and bounded concurrency:

```bash
OLLAMA_HOST=172.17.0.1:11434 \
OLLAMA_CONTEXT_LENGTH=32768 \
OLLAMA_MAX_LOADED_MODELS=1 \
OLLAMA_NUM_PARALLEL=1 \
OLLAMA_FLASH_ATTENTION=1 \
OLLAMA_KV_CACHE_TYPE=q8_0 \
ollama serve
```

Then configure the Vexa stack, replacing `172.17.0.1` if Docker reported a different gateway:

```dotenv
VEXA_LLM_PROVIDER=openai-compat
VEXA_LLM_BASE_URL=http://172.17.0.1:11434/v1
VEXA_LLM_API_KEY=ollama
VEXA_LLM_MODEL=gemma4:12b
ANTHROPIC_BASE_URL=http://172.17.0.1:11434
ANTHROPIC_AUTH_TOKEN=ollama
VEXA_AGENT_MODEL=gemma4:12b
VEXA_MEETING_MODEL=gemma4:12b
VEXA_MODEL_ALLOWLIST=gemma4:12b
CLAUDE_CODE_DISABLE_THINKING=1
MAX_THINKING_TOKENS=0
CLAUDE_CODE_MAX_OUTPUT_TOKENS=4096
```

Do not use `OLLAMA_HOST=0.0.0.0:11434` for this local-only setup. Confirm with `ss -ltn` that Ollama
listens only on the Docker bridge address before sending a meeting bot. Disabling extended thinking
keeps a short post-meeting report from consuming a large reasoning budget; the output cap adds a
second bound for single-GPU tests.

## Option A — dispatch a report when the meeting ends

Fire a one-shot [dispatch](/core/agents) the moment a call wraps (e.g. from your own meeting-end hook):

```bash
curl -X POST "$API_BASE/agent/invocations" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{
    "runner":"claude-code",
    "workspaces":[{"id":"u_jane","mode":"rw"}],
    "trigger":"scheduled",
    "start":{"entrypoint":{"inline":"Write a report for the meeting that just ended: summary, decisions, action items with owners, and links to the people and companies involved. File it in the workspace."}}
  }'
# → 202 {"workload_id":"agent-..."}
```

The agent reads the latest transcript and existing entities, then commits the report. Retrieve it from the
workspace:

```bash
curl -H "X-API-Key: $API_KEY" "$API_BASE/agent/workspace/tree"
curl -H "X-API-Key: $API_KEY" "$API_BASE/agent/workspace/file?path=meetings/2026-06-29-acme.md"
```

## Option B — a standing routine

If you'd rather not wire a hook, run it on a schedule that sweeps recent meetings:

```bash
curl -X POST "$API_BASE/agent/routines" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{
    "name":"Meeting reports",
    "cron":"0 * * * *",
    "prompt":"For any meeting that ended in the last hour and has no report yet, write one: summary, decisions, action items with owners. File each in the workspace.",
    "run_now":true
  }'
# → 201 {"routine":{...},"job_id":"job_...","ran_now":true}
```

## What you get

The report is **grounded**, not a bare summary — it's anchored in the accumulated context the workspace
already holds, and each run leaves the workspace more complete (people, companies, decisions linked). See
[Knowledge agent](/how-to/chat-workspace).

## Going live instead

To surface decisions and action items **during** the call rather than after, run the live copilot —
`POST /agent/meeting/start` then stream cards from `GET /agent/meeting/stream`. See
[Meeting copilot](/how-to/live-copilot) and the [Agent API](/api/agent#live-meeting-copilot).

<Note>
Routines and dispatches are workspace writes, so they need a **trusted** trigger (`message`/`scheduled`),
which mounts the workspace `rw`. Untrusted triggers are propose-only — see
[Governance](/architecture/governance).
</Note>
